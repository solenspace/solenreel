**Spec 15 complete.** Client-side click tracker landed. Branch `feat/spec-15-click-tracker-hook` off `development`. **Spec 12 follow-up (same branch, same PR #11):** live Playwright smoke against `pnpm dev` (signed in as `smoke@reel.dev`) revealed the design tension between reel's portrait posters (`192×288`) and YouTube's 16:9 trailer iframes. The `1.3× scale` in `mode='overlay'` was designed for 16:9 containers (banner / movie-modal hero) where it crops the YouTube branding chrome while filling the container with video; in a 2:3 portrait container the iframe letterboxes — only ~140 px out of 288 px shows actual video content; the top ~74 px and bottom ~74 px are black bars. Composited at `0.7` opacity over a portrait poster, the result is a muddy "dim poster with a narrow video strip in the middle" that doesn't match the editorial direction (`CLAUDE.md` cites Letterboxd, Criterion, magazine reviews — none autoplay trailers on portrait posters). Plus the cross-origin YouTube iframe takes 1–2 s of visually-transparent loading time before any pixels render, so the user sees no hover affordance for the first second. Fix: `home.jsx` no longer passes `hoverPlayer` to its `<Row>` — reel home renders editorial static posters; the trailer plays *only* on click → `/movie/:id` (spec 13's full-bleed audio-on hero, where the 16:9 container makes `mode='full'`'s `1.3× scale` work as designed). All spec-12 infrastructure stays in place: `useTrailerOnHover`, `hover-store`, `HoverTile`, `mode='overlay'` on `TrailerPlayer`, the 14 hook + wrapper tests, and the Tile entity's `posterOverlay` + `rootRef` extension props. A future 16:9-shaped tile variant (e.g., a backdrop-tile row for trending or recent-releases) can opt into hover trailers without code rework. Specs 18 (for-you row) and 21 (intent-results row) — both opted into `hoverPlayer` per spec 12 design decisions — should re-evaluate before implementation: if their rows also use portrait posters they'll hit the same visual issue and should default off; if they use a 16:9 backdrop variant they can opt in. ## Architecture decisions (append-only log)

- 2026-05-06 — **`<article tabIndex={-1}>` + `useEffect` focus on mount, so `Esc` survives the autoplay iframe (spec 13 follow-up)**: the original spec 13 implementation wired `useKeyDown('Escape', () => navigate(-1))` at window scope, expected to work because the click that navigates to `/movie/:id` puts focus on the `<button>` that gets unmounted, leaving the document `<body>` focused. Live smoke against `pnpm dev` proved otherwise: `<TrailerPlayer mode='full' playing>` mounts a YouTube iframe inside the same React tick the article element appears in, and the iframe's `autoplay=1` immediately (within ~50 ms of mount) requests focus to play. From that moment the iframe is the active element of the page; `keydown` events fire on the iframe's window, not the parent's, and the parent's `addEventListener('keydown')` never receives them. Fix: `<article>` gets `tabIndex={-1}` (focusable but not in the Tab order — the article isn't an interactive control, it's a programmatic focus target only) plus a `useEffect(() => articleRef.current?.focus({ preventScroll: true }), [id])` that races React's commit phase against the iframe's autoplay focus grab, and wins because React's effect fires before the iframe finishes loading its embed. `preventScroll: true` keeps the call from auto-scrolling the page into the article (which would scroll past any sticky header chrome). The `id` dep re-focuses on intra-page navigation (e.g., clicking a tile in the v1.1 "more like this" row that lands on a new `/movie/:id` without unmounting the article wrapper). `focus:outline-none` on the article suppresses the default `:focus-visible` ring on the article itself — the article is the focus target, not the visible chrome; the ring belongs on actual interactive controls (back-arrow `<button>`, links, tiles). This pattern generalizes: any future page that mounts a focus-grabbing third-party embed (Stripe checkout, Vimeo, iframe captchas) should follow the same `tabIndex={-1}` + auto-focus pattern. Trade-off: a screen-reader user landing on `/movie/:id` will hear the article element announced first (the SR will read the heading inside it), which is actually closer to the editorial intent than starting reading from the YouTube player; not regressive.

- 2026-05-06 — **`useKeyDown(key, handler, enabled)` lives in `src/shared/lib/`, not co-located with the page (spec 13)**: spec 13 step 5 said "Use a small shared hook `useKeyDown(key, handler)` at `src/shared/lib/use-key-down.js` (will be reused in spec 22)". Implementation captures the handler in a `useRef` so callers can pass an inline `() => navigate(-1)` arrow without re-binding the global `keydown` listener every render — the listener attaches once per `(key, enabled)` change and reads `handlerRef.current` at fire time. The `enabled` flag (default `true`) is the third parameter so future consumers (spec 22's search overlay needs `Esc` active only while the dropdown is open) can gate subscription declaratively without conditional rendering of the consumer component. Two effects rather than one (`handlerRef` write effect + listener-attach effect) keeps the listener stable across handler-identity changes — important because the spec 13 page passes a fresh closure each render and we don't want add/remove churn on the window. The hook lives in `shared/lib` (not `shared/ui` or `features/`) because it's a generic browser-event utility with no domain coupling — same neighborhood as `use-debounce.js` / `use-loading-too-long.js` / `use-document-title.js`.

- 2026-05-06 — **Movie-detail page calls `useMovieDetails` AND `useMovieVideos` in parallel (spec 13)**: `useMovieDetails(id)` already returns `videos` via TMDB's `append_to_response=videos,credits,similar,images` parameter, so a separate `useMovieVideos(id)` call produces a second request whose payload partially overlaps. Spec 13 success criterion #6 says "Network panel shows exactly two TMDB requests on first load (`movie/{id}` + `movie/{id}/videos`)" — calling both is the spec literal, not a workaround. Worth it because (1) the lighter `movie/{id}/videos` endpoint resolves before the heavier `movie/{id}?append_to_response=...` payload, so the trailer can paint as soon as the videos arrive even while details are still in flight; (2) react-query's separate cache keys (`['tmdb', 'movie', id]` vs `['tmdb', 'movie-videos', id]`) mean either response can be reused independently — Banner already consumes `useMovieVideos`, so the home → movie-detail navigation path warms its cache for the next visit; (3) the trailer-key derivation prefers `videosQuery.data` (lighter, faster) and falls back to `details.data?.videos` if the videos request errors. Net effect: trailer paints faster on slow networks at the cost of one ~5 KB extra response.

- 2026-05-06 — **`<MoreLikeThisRow>` feature-flagged behind `VITE_FEATURE_MORE_LIKE_THIS` and gated at the parent (spec 13)**: spec 13 step 3 marks the similar-movies row as "optional v1.1 deliverable" and instructs `import.meta.env.VITE_FEATURE_MORE_LIKE_THIS` as the gate. The check happens at the page level (`MORE_LIKE_THIS_ENABLED && <MoreLikeThisRow ... />`) rather than inside the row component, so when the flag is off the `useByGenre` query never fires — important because (a) success criterion #6 requires "exactly two TMDB requests on first load" and an in-component flag check would still call the hook unconditionally before short-circuiting in the JSX; (b) hooks can't be called conditionally at the React rules level. Default off in v1; flip the env var to `true` (in `.env.local`, not a committed template per the gitignore policy) for v1.1. The component itself returns `null` while pending or on error, so even when on it never blurs the page on slow networks.

- 2026-05-06 — **`home.jsx` does NOT opt into spec-12 `hoverPlayer`; portrait posters + 16:9 YouTube trailers don't compose visually (spec 12 follow-up)**: spec 12 step 5 mandated "Update home (`src/app/pages/Home.jsx`) to pass `hoverPlayer` to its `<Row>` so each tile gets the slot." After landing the wiring and running a live Playwright smoke against `pnpm dev`, the design failure became visible: reel's posters are portrait (`tileVariants.grid.posterClass: 'h-72 w-48'` = 192×288), YouTube's iframe is 16:9. `mode='overlay'`'s shared `transform: translate(-50%, -50%) scale(1.3)` is designed for 16:9 containers (banner, modal hero) where it crops out the YouTube logo/chrome while filling the container; in a 2:3 portrait container the iframe oversizes to 250×374 but the YouTube player still letterboxes its 16:9 video to a ~140 px middle band — top ~74 px and bottom ~74 px are black bars composited at `0.7` opacity over the poster, producing dim banding rather than editorial elegance. Cross-origin YouTube embed load time (1–2 s) compounds the issue: for the first second after hover, the iframe is visually transparent and the user sees no hover affordance at all. Reel's stated editorial inspiration (`CLAUDE.md`: "editorial film coverage (Letterboxd, Criterion, magazine reviews). It is dense, typographic, low-chrome") doesn't autoplay trailers on portrait posters — Letterboxd uses a metadata-on-hover overlay; Criterion is fully static. Fix: opt the home row out of `hoverPlayer`; the trailer plays *only* at the click destination `/movie/:id` (spec 13), where `mode='full'`'s same `1.3× scale` works correctly inside a 16:9 hero. **All spec-12 infrastructure stays in code** — `useTrailerOnHover`, `hover-store`, `HoverTile`, `mode='overlay'`, the 14 hook + wrapper tests, the Tile entity's generic `posterOverlay` + `rootRef` props — so any future 16:9 tile variant (backdrop-shaped trending row, hero rail) can opt in without rework. **Specs 18 and 21 should re-evaluate** before implementation: their rows currently inherit the `hoverPlayer` opt-in from spec 12 design notes, but if they use the same portrait `variant='grid'` posters they'll hit the same visual failure and should default off; the right opt-in is a 16:9 tile variant added later. The deviation from spec-12 step 5 is documented here rather than as a spec-text amendment because the design failure was only discoverable with running code + a real YouTube iframe — the unit tests confirmed the state machine but not the visual composition.

- 2026-05-06 — **Spec 12 hover trailer wired via a feature-level `<HoverTile>` wrapper, not a `Tile.HoverPlayer` slot inside `entities/movie/tile.jsx`**: the spec text said "Update `entities/movie/tile.jsx` to expose a `Tile.HoverPlayer` slot" + "the slot calls `useTrailerOnHover(movie.id)`". Implementing that literally would have imported the hook + `<TrailerPlayer>` from `features/trailer/` into the entity layer — an upward FSD import (entity → feature) that `code-standards.md` strictly forbids ("Imports flow upward only"). The wrapper-component pattern at `src/features/trailer/hover-tile.jsx` calls the hook, conditionally renders the overlay player, and feeds it into Tile's two new generic extension props (`posterOverlay?: ReactNode` and `rootRef?: React.Ref<HTMLElement>`) — same opt-in surface at every layer (Page → Row → Tile), same test outcomes, same DOM in every state, but the entity now has zero feature dependencies. `Row` decides between `<Tile>` and `<HoverTile>` via a small `<RenderedTile>` helper used by both eager and lazy slots. Trade-off: the spec's compound-component slot ergonomics are replaced by a wrapper pattern; consumers gain `<HoverTile>` (a feature-layer concept) instead of `<Tile.HoverPlayer />` (which would have lived in entities). The wrapper pattern is a documented React composition idiom (`vercel-composition-patterns/state-decouple-implementation.md` — "the provider component should be the only place that knows how state is managed; UI components consume the context interface"); here, `<HoverTile>` is the provider that knows the hover state machine, while `<Tile>` consumes only its generic extension contract. Future hover-adjacent specs (spec 13 full-bleed audio, spec 18 for-you reasoning) can extend the same `posterOverlay` slot for their own overlays without re-importing into entities.
- 2026-05-06 — **`useTrailerOnHover` returns `{ ref, state, videoKey, onError }`, not `{ ref, state }` (spec 12 deviation)**: the spec literal said the hook returns `{ ref, state }` only. Two additional return values are required by the wrapper's failure-mode handling: `videoKey` is needed by `<HoverTile>` to construct the `<TrailerPlayer videoKey={...}>` overlay (the spec listed this as a discoverable internal but not a return value); `onError` is needed to plumb `react-player`'s embed-rejection callback back into the hook's state machine — spec-12 §"Failure modes" #2 mandates `state='unsupported'` on YouTube `onError`, which can only happen if the slot wires the player's `onError` prop to a hook-owned setter. Returning the callback from the hook keeps the state machine encapsulated (the wrapper can't directly call `setState`); the hook's `useCallback`-stable identity prevents re-render churn on the player.
- 2026-05-06 — **Global single-player invariant uses a Redux slice + `useStore` snapshot, not custom DOM events (spec 12)**: the spec mentioned "a custom event the others listen for and force-unmount their players" as one option, with the noted alternative of "a global signal `currentlyHoveringTileId` on a small store at `src/features/trailer/hover-store.js` (Redux slice, since Redux is already wired). This is the chosen path." Implementation: each instance of the hook reads `selectIsCurrentlyHovering(state, movieId)` via `useSelector` — when the slice's `hoveringTileId` flips away from this tile, the cleanup effect resets local state to `'idle'` and clears all timers. Race-free release of the slot uses `useStore().getState()` inside the leave-timer (not `useSelector`) so the timer reads the *current* slice value at fire time, not a snapshot from when the listener was installed; if tile A's leave-timer fires after tile B has already claimed the slot, A's `claimedSlotRef` is still `true` but the `selectHoveringTileId(getState()) === movieId` guard prevents A from clobbering B's claim. StrictMode double-mount is a non-issue because the dispatch is idempotent and the store getter always reads truth. `redux-thunk` is not needed — the bare `getState()` snapshot pattern keeps the dispatch contract simple.
- 2026-05-06 — **`prefers-reduced-motion: reduce` parks `state='unsupported'` permanently, never `'idle'` (spec 12)**: the spec said the hook "Honors `prefers-reduced-motion`: sets `state = 'unsupported'` and never mounts the player". Choosing `'unsupported'` rather than `'idle'` distinguishes "user explicitly opted out of motion" from "no hover yet but motion is fine" — the slot's `state !== 'playing'` short-circuit returns `null` for both, but downstream specs (e.g., spec 22 a11y polish) can render an explicit static-poster affordance in the `'unsupported'` branch without false-positive matches against tiles waiting on a hover. The hook also subscribes to the OS preference's `change` event so a runtime flip of the user setting takes effect immediately on the next render — important for users who toggle the OS setting mid-session.
- 2026-05-06 — **`TrailerPlayer` relocated to `features/trailer/` with `mode='full'|'overlay'` prop (spec 12)**: the player previously lived at `src/shared/ui/trailer-player.jsx` (post-spec-01); spec 12 wanted it at `src/features/trailer/trailer-player.jsx` so the entire trailer concern (player + hover hook + slice + wrapper) is co-located. `git mv` preserves blame; the two existing call sites (`src/widgets/banner/banner.jsx`, `src/features/movie-modal/movie-modal.jsx`) get one-line import-path edits. The `mode` prop branches the wrapper styling — `mode='full'` (default) keeps the previous `relative overflow-hidden` wrapper + 1.3× scale (preserves banner/modal-hero behavior unchanged); `mode='overlay'` switches to `pointer-events-none absolute inset-0` with `style={{ opacity: 0.7 }}` so the trailer fades into the poster's positioned-relative wrapper without intercepting the parent `<button>`'s clicks. The 1.3× scale is shared across both modes because it crops out the YouTube branding chrome (logo, "More videos") regardless of which surface owns the player. The new `onError` callback is wired in both modes — spec 12 needs it; spec 13 (full-bleed) may use it for the same purpose.
- 2026-05-06 — **`Tile` gains `posterOverlay?: ReactNode` + `rootRef?: React.Ref<HTMLElement>` as generic extension props (spec 12)**: rather than coupling Tile to `features/trailer/` types, the entity exposes two layer-agnostic seams. `posterOverlay` is rendered absolutely over the poster via a new `<div data-slot="poster-frame" class="relative">` wrapper that's only inserted when an overlay is provided — Tiles without overlay keep the previous DOM byte-for-byte (zero regression on existing tests; the rendered output of `<Tile movie={...} variant="grid" />` is identical to spec 10's). `rootRef` forwards through to the underlying `<button>` or `<article>` via type-narrowed casts (`React.Ref<HTMLButtonElement>` vs `React.Ref<HTMLElement>` per the existing tag-swap branch). These seams are not feature-specific: spec 18 (for-you reasoning) can reuse `posterOverlay` for a "Because you watched X" chip; spec 22 (a11y polish) can use `rootRef` for focus-trap edges or escape-key handlers. The pattern is the FSD-compliant version of "extension slots in entities" — entities provide the contract; features fill it.

- 2026-05-06 — **`Tile` is a true compound component with a shared `TileContext` exposing `{ movie, variant }` (spec 10)**: subcomponents (`Tile.Poster`/`Tile.Body`/`Tile.Title`/`Tile.Meta`/`Tile.MoodTags`/`Tile.Score`/`Tile.Reasoning`) read context independently — zero prop drilling, zero render-prop indirection. Per `vercel-composition-patterns/architecture-compound-components.md`.
