## Architecture decisions (append-only log)

- 2026-05-05 — **Slice replaces Firebase `uid`/`email`/`displayName` shape with Supabase `Session` + `status` + `error` (spec 05)**: post-spec-04 the user-slice still carried Firebase-derived state (`{ user: { uid, email, displayName } | null }`). Replaced with `{ session: Session | null, status: 'idle' | 'loading' | 'authenticated' | 'unauthenticated', error: AppAuthError | null }`. `selectUser` is now a derivation (`state.user.session?.user ?? null`) that returns the Supabase `User` shape (`id`, `email`, `app_metadata`, `user_metadata`, etc.) — `uid` is gone, consumers reading `user.email` keep working unchanged because `User.email` is the same field name. The new `status` field gives layouts a tri-state ("booting" / "in-flight auth call" / "settled") that the old boolean-based `authChecked` couldn't express cleanly.
- 2026-05-05 — **`useAppDispatch` lives in `src/shared/lib/use-app-dispatch.js` with a generic `ThunkDispatch<unknown, undefined, UnknownAction>` type, NOT in `app/store.js` (spec 05 FSD decision)**: typed dispatch hook needed so `dispatch(thunk).unwrap()` typechecks under JSDoc + checkJs. Initial draft put it in `app/store.js` (alongside the store) — works for `app/pages/*` but ESLint's `import/no-restricted-paths` immediately blocked `widgets/header/header.jsx` from consuming it (widgets cannot import from `app/`). Moving the hook to `shared/lib` solves the FSD constraint; the cost is the dispatch type is `ThunkDispatch<unknown, ...>` rather than the precise `typeof store.dispatch` (which would require importing the store and reintroduce the violation). For our use case (thunks don't read state through dispatch — they use `useSelector`), the unknown-state generic is fully sufficient.
- 2026-05-05 — **Slice's `extraReducers` deliberately omits `.fulfilled` cases for the three thunks (spec 05)**: `useAuthSession.onAuthStateChange` is the single producer of session writes (via `setSession`). If the slice ALSO handled `signIn.fulfilled` by writing the session, two dispatches race during a normal sign-in — the thunk's resolved-with-session and the listener's SIGNED_IN event arrive in the same microtask. The thunk-side write would briefly land first, then `INITIAL_SESSION` could overwrite with stale data depending on timing. Omitting `.fulfilled` makes the listener authoritative; the thunk-side resolve is informational only. Behavior verified in `auth-actions.test.js` — after a happy-path `signIn` dispatch, slice status stays `'loading'` until a separate `setSession` reducer call fires.
- 2026-05-05 — **Dropped module-level `didSubscribe` guard from `useAuthSession` (spec 05 deviation from initial plan)**: plan v1 included a module-level `let didSubscribe = false` guard inspired by `vercel-react-best-practices/rules/advanced-init-once.md`, with the intent of preventing double-subscribe under React 19 StrictMode dev double-mount. On implementation, the guard fights React's standard cleanup contract: in StrictMode the cleanup unsubscribes (correctly), then the second mount checks `didSubscribe = true` and returns early — leaving NO live subscription. To make it work the guard would need to be one-way (never reset), which then breaks subsequent legitimate mount-after-unmount in tests. The canonical React 19 pattern (and what Supabase's own docs use) is plain `useEffect` with subscribe-on-mount + unsubscribe-on-cleanup; StrictMode's brief subscribe→unsubscribe→subscribe dance is harmless because subscriptions are properly cleaned between mounts. In production (non-StrictMode), `AuthSessionGate` mounts once at app boot and never unmounts, so there's only one subscription for the app's lifetime regardless.
- 2026-05-05 — **`useAuthSession` mounts via `AuthSessionGate` wrapper, not by calling the hook in `App.jsx`'s body (spec 05 user-confirmed decision)**: spec 05 step 5 said "stub the call here from `App.jsx` if spec 08 hasn't reorganized providers yet". The wrapper-component path was chosen instead because (a) `App.jsx` today is a single-responsibility router shell (`<RouterProvider router={router} />`) and adding an auth-listener side effect there would mix concerns, (b) the `AuthSessionGate` boundary is named, testable, and discoverable, (c) when spec 08 introduces `app/providers/`, the gate moves there with one import-path change. Cost: one extra ~6-line component file under `entities/user/`.
- 2026-05-05 — **Logout-redirect responsibility lives in `AppLayout`, not in the `signOut` thunk (spec 05)**: `AppLayout` watches `selectAuthStatus` via `useEffect` and pushes to `/auth/login` when status flips to `'unauthenticated'`. The `signOut` thunk does NOT navigate. This is the single source of truth: any path that nulls the session — explicit sign-out button, expired-token refresh failure, programmatic clear, external-tab logout via Supabase's BroadcastChannel — reaches the same redirect. AuthLayout symmetrically handles the inbound redirect on `'authenticated'`. Verified end-to-end via Playwright MCP smoke.
