# reel — AI Workflow Rules

## Spec-driven workflow

- Work happens inside numbered specs in `specs/`. Each spec is a single unit with: **Goal · Dependencies · Design Decisions · Implementation · Success Criteria**.
- One spec at a time. Do not interleave specs. Do not partially implement spec N while starting spec N+1.
- A spec is done when all five verification gates (see `code-standards.md`) pass on its branch and `progress-tracker.md` is updated.

## Splitting rule

Split a spec into smaller specs when it crosses any of these boundaries:

- **UI + Edge Function + DB schema** in one go. Land the schema first, then the function, then the UI.
- **Recommendation logic + LLM logic** in one go. The two have different test strategies and should not co-mutate.
- **Auth changes + new RLS-protected table** in one go. Auth and RLS are each load-bearing; review them separately.
- **Cross-FSD-layer refactor** while shipping a feature. Refactor and feature land as separate specs.

If you find yourself reaching across boundaries inside a single spec, stop and split.

## Protected files

Do not edit these without explicit user approval:

- `supabase/migrations/*` — past migrations are immutable history. New schema changes go in a new numbered migration.
- `supabase/types.gen.js` (or its JSDoc-typedef equivalent generated by the Supabase CLI) — this is codegen output.
- `src/components/ui/*` — any primitives installed by a CLI tool (e.g. shadcn-equivalent for React+JS) are CLI-managed; modify via the tool, not by hand.
- `.claude/agents/*` — agent definitions are owned by this run's bootstrap. Changes go through a deliberate agent-revision spec.
- `context/*` (except `progress-tracker.md`) — these files are append-only history. If implementation changes them, surface the change explicitly and update the relevant context file _before_ continuing.

## Context-file discipline

- The five context files **other than** `progress-tracker.md` are the project's invariants and conventions. They mutate slowly and only with deliberation.
- `progress-tracker.md` is the only context file that mutates frequently. Update it after every meaningful change: completed work, new in-progress, new open questions, new architecture decisions.
- When code drift conflicts with a context file, fix the context file _first_ — context is the source of truth, not the code.

## Decision protocol

When the user's request is ambiguous, the agent:

1. Re-reads the relevant context files (`architecture.md` Invariants section first).
2. If the answer is in the context, follows it. No question asked.
3. If the answer crosses an invariant, surfaces the conflict to the user — does not silently break the invariant.
4. If the answer is outside the context entirely, asks one focused clarifying question rather than guessing.

Do not silently invent infrastructure (new tables, new env vars, new providers). Surface and confirm.

## Verification gates per spec

Every spec must pass these before it is marked done. Order matters: don't move on with red.

1. **`pnpm typecheck`** — JSDoc-driven `tsc --noEmit`.
2. **`pnpm lint`** — ESLint + Prettier.
3. **`pnpm test`** — Vitest unit tests; new tests must accompany every behavioral change.
4. **`pnpm build`** — Vite production build succeeds with no warnings about unresolved imports or missing env vars.
5. **Manual smoke test** — for UI specs: load the dev server, exercise the new flow, confirm no console errors.
6. **Edge Function smoke test** — for any spec touching `supabase/functions/`: `supabase functions serve <name>` locally, hit it with the documented request, confirm a JSON-schema-conforming response.

If a gate fails, the spec stays open. Do not paper over with skipped tests, suppressed warnings, or `// @ts-ignore`. Diagnose root cause.

## Agents (use them; don't bypass them)

- **`fsd-architect`** — invoke after any change that touches FSD layer boundaries, adds a new file under `src/`, or touches data-fetching boundaries.
- **`test-writer`** — invoke when adding tests for hooks, components, or Edge Functions; do not write tests by hand without checking patterns.
- **`prompt-engineer`** — invoke when authoring or revising any prompt sent to OpenRouter, or any JSON schema for an LLM response.

Agents are not advisory — they are gating reviewers for the surfaces they cover.

## What you do not do

- You do not invent new agents. If a domain need emerges, surface it; only adopt agents that already exist in validated registries (vercel-labs, anthropic, community).
- You do not invent new skills. Skills come from `skills-lock.json`, sourced from real repos.
- You do not add a new external dependency without it appearing in a spec's "Dependencies" section.
- You do not skip verification gates. Failing tests are blockers, not nuisances.
- You do not silently change `architecture.md` invariants. They are load-bearing.
